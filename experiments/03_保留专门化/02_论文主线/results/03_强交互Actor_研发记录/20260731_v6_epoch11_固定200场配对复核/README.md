# v6 epoch-11 固定200场配对复核

## 目的

确认v6 epoch-11在50场monitor上的峰值是否是真实提升，还是挑选checkpoint造成的偶然高点。

## 协议

- 固定manifest：`dense_validation_monitor_v1`，200场；
- seed：`20260731`；
- 基线：冻结5A；
- 候选：v6 epoch-11；
- 两组均由单个Actor全程独立控制5台机器人；
- 禁用双Actor、oracle和规则让行；
- 两组按相同scenario ID和相同顺序串行运行。

## 总结果

| 指标 | 5A | v6 epoch-11 | 变化 |
| --- | ---: | ---: | ---: |
| agent success | `0.719` | `0.786` | `+0.067` |
| collision | `0.281` | `0.189` | `-0.092` |
| unresolved | `0.000` | `0.025` | `+0.025` |
| full success | `67/200 = 0.335` | `89/200 = 0.445` | `+0.110` |
| timeout | `0/200` | `24/200 = 0.120` | `+0.120` |
| mean env steps | `26.96` | `69.77` | `+42.81` |
| mean steps（排除timeout） | `26.96` | `38.37` | `+11.41` |

full-success逐场配对为：两者都成功`49`场、仅5A成功`18`场、仅v6成功`40`场、两者都失败`93`场。McNemar exact `p=0.00535`，所以v6的full-success提升不是本次200场中的随机波动。

但v6新增了`24`个timeout，其中`8`场5A原本能够full success。平均步数增加`158.8%`，说明碰撞下降的一部分仍然来自保守等待。

## 按冲突边分层

| 冲突边 | 场景数 | 5A full | v6 full | v6 timeout |
| --- | ---: | ---: | ---: | ---: |
| 0 | 7 | `1.000` | `0.857` | `0.000` |
| 1 | 45 | `0.444` | `0.667` | `0.133` |
| 2 | 61 | `0.393` | `0.508` | `0.115` |
| 3+ | 87 | `0.184` | `0.253` | `0.126` |

v6在有冲突的三个分层上均提高full success，但timeout在这些分层中都约为`11%~13%`。在7个无冲突场景上，v6还把5A的`7/7`降低为`6/7`，平均步数从`19.43`增加到`43.14`。

## 结论

v6 epoch-11确实学到了有效的Dense避碰，不应再描述成“50场偶然峰值”。但它没有解决独立Actor的完成效率和等待问题，不能作为最终Dense Actor：

1. full success仍只有`0.445`；
2. `12%`的场景触发timeout，而5A为`0%`；
3. 平均步数是5A的`2.59`倍；
4. 无冲突场景也出现速度和成功率退化。

因此不继续为这个已确认存在系统性timeout的checkpoint运行完整1000场。下一步使用已锁定的v8协议重新训练：保留5A warm-start和独立Dense rollout，移除统一减速目标、隐藏让行优先级和冲突的Q归一化。

两者存在互补性：理想逐场选择的full-success并集为`107/200 = 0.535`。这只说明未来Gate可能有价值，不代表现在的v6已经合格；必须先训练出timeout可接受的独立Dense Actor。
